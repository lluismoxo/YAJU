Agent Academy

Welcome to Agent Academy, a practical course on building and operating AI agents. It starts from what an agent actually is and ends with running a fleet of them in production, assuming no prior experience.

Work through the eight modules in order. Each one builds on the last, and together they take you from your first agent to a system you can put in front of real users.


    • 01 — What an AI agent actually is

      A language model answers. An agent acts. The difference is a loop: it receives a goal, decides on a step, takes that step using a tool, reads the result and decides again, repeating until the goal is met or it runs out of room to try.

      That loop is the whole idea. Everything else in this course is about making it reliable: what the agent can see, what it is allowed to do, and what happens when a step goes wrong.

      A quick test. If taking away its tools would leave something still useful, you have a chatbot. If taking them away makes it pointless, you have an agent.

    • 02 — How an agent works, part by part

      Four parts show up in almost every agent. The model does the reasoning. The instructions set the role, the constraints and the definition of done. The tools are the actions it can take: an API call, a query, a file written. The memory is what it carries between steps, usually the running transcript plus whatever you deliberately hand it.

      Around those sits the runtime: the thing that actually executes the loop, enforces the limits and records what happened. Frameworks give you the first four parts. The runtime is what turns them into something you can put in front of real users.

      Knowing which part failed is most of debugging. A wrong answer is usually bad context, not a bad model.

    • 03 — Getting a good agent: build, fork or adopt

      There are three honest routes. Write it yourself with an SDK, which gives you full control and costs the most time. Fork one from a public repository, which is fast but inherits assumptions you did not make. Or take a production-ready agent from a catalogue such as the Yaju Agent Hub and adapt it: browse, fork, publish, improve.

      Whichever route you pick, the agent is not finished the first time it works. Run it against real cases, not the three you had in mind while writing it. Decide what a correct answer looks like before you read the output, or you will grade it on impressions.

      Then personalise it to your data, your naming and your edge cases. A generic agent that almost fits is often worse than none at all, because people stop trusting it after the second wrong answer.

    • 04 — Tools, context and capabilities

      An agent is only as capable as what you hand it. Tools should be few, precisely named and narrowly scoped: one that reads orders, not one that manages the database. Vague tools produce vague decisions.

      Context is the other half. Give it the specific records this task needs, not the whole knowledge base. More context is not better: it costs money, slows the run, and buries the one relevant line among a thousand irrelevant ones.

      Credentials deserve their own rule. The agent should never hold a secret. It asks for the action, and the platform attaches the credential at the moment of the call, so a leaked prompt never becomes a leaked key.

    • 05 — Limits, failure modes and honest expectations

      Autonomy is the part that oversells itself. A long unsupervised loop compounds its own mistakes: one bad assumption at step three quietly shapes steps four through twenty. Agents also fail in ways ordinary software does not. They invent plausible details, they retry the same wrong approach, and they report success they did not achieve.

      So bound them. Cap the loop. Cap the retries. Require human approval before anything irreversible: deleting data, messaging a customer, spending above a threshold.

      And prefer few good agents to many mediocre ones. Ten half-working agents cost more, break more often and erode trust faster than two that do their job properly. Retiring an agent is a legitimate outcome, not a failure.

    • 06 — Packaging an agent for the outside world

      An agent that only runs on your machine is a prototype. Packaging it means making it reproducible: typed inputs and outputs so callers know what to send and what comes back, pinned dependencies, and configuration kept outside the code.

      Version it like software, because it is software. Keep it in Git, point at a specific version, diff two versions, and roll back to the previous one when a change makes things worse.

      Write down the boundaries as well: what the agent is for, what it must never do, and which checks it has to pass. That note is what lets somebody else run it without asking you first.

    • 07 — Deploying an agent on Yaju

      Deployment is where an agent stops being yours alone. On Yaju it gets an identity and an owner the moment it runs, so it appears in one catalogue instead of living in somebody’s terminal.

      From there the control plane attaches what it needs: credentials resolved at runtime from the organization vault, access rules checked before each call, and a full session trace written as the run happens. You deploy from the CLI, the same commands work inside your existing pipelines, or self-hosted inside your own environment when the data cannot leave it.

      Nothing about how you built the agent has to change. Bring your own agent, whatever framework produced it, and the same rules apply to it as to everything else.

    • 08 — Operating a fleet with Yaju Agent Systems

      One agent is a project. Thirty agents is an operations problem, and it arrives sooner than most teams expect.

      Operating a fleet means four things at once: knowing what exists, controlling what each agent can reach, seeing what it did, and knowing what it cost. Yaju Agent Systems covers those: a catalogue with an owner per agent, policy enforced at the moment of action, traces and evals that can halt a bad run, and spend attributed by agent, user, provider and model with hard limits that stop an overrun instead of reporting it afterwards.

      The goal is deliberately unglamorous, and it is the whole point: agents that behave like the rest of your production software, so that running more of them does not mean trusting them less.
